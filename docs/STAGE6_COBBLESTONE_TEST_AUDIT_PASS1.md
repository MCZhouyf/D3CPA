## Actual Action Schema

From `dc3pa.contracts.Action._validate_shape`:

- `mine`: required args `{"obj", "tool"}`
- `craft`: required args `{"obj", "materials", "platform"}`
- `equip`: required args `{"obj"}`

Additional shape details:

- `craft.obj` must be a mapping with exactly one output item.
- `craft.materials` must be a mapping of positive finite numeric quantities.
- `mine.tool` is mandatory even if the tool is missing in inventory.

## Knowledge Conflict Propagation

Knowledge feasibility is implemented in `dc3pa.reliability.KnowledgeReliabilityStrategy`.

- Explicit action prerequisites are extracted from the action schema:
  - `mine` requires tool quantity `1.0`
  - `craft` requires materials and platform
- Learned memory prerequisites are loaded through `DependencyGraphStore.prerequisites_for(target)`.
- The strategy projects the inventory prefix with `project_inventory(plan, state)` so earlier plan steps can satisfy later ones.
- Any unmet prerequisite produces:
  - `DimensionScore.dimension == "knowledge"`
  - `available == True`
  - `probability == 0.0`
  - `hard_conflict == True`
  - structured `evidence["missing"]` entries including `item`, `relation_type`, `required`, `available`, `sources`

Therefore a `mine cobblestone` step without a prior crafted/equipped `wooden pickaxe` can be tested directly and will produce an auditable hard knowledge conflict.

## Adaptive Trigger Behavior

`AdaptiveTriggerSession.observe(...)` computes `low_confidence` as true when any of these holds:

- `hard_conflict == True`
- a probability is unavailable
- monitored confidence is unavailable
- monitored confidence is below threshold

If `hard_conflict == True`, the next interval is forced to `minimum_interval`, regardless of the mean confidence. This means a high model score cannot suppress a knowledge hard conflict.

## Patch / Revision Semantics

Current revision behavior is compatible with the controlled test design:

- `PlanEditor.apply(...)` creates a new `Plan`
- revised plan `version = original.version + 1`
- revised plan `parent_plan_id = original.plan_id`
- revised plan gets a fresh `plan_id`
- `PatchApplication.earliest_changed_index` is returned from the editor
- `AdaptiveCognitiveControlPlanner.plan_with_outcome(...)` restarts from `earliest_changed_index`
- `AdaptiveTriggerSession.restart_after_revision(...)` clears `_recent` confidence history and forces the next window with reason `post_revision_validation`

This satisfies the required properties:

- version increments
- parent lineage is set
- evaluation resumes from the earliest changed position
- old trigger confidence history is discarded

## When Stage 6 Calls The Controller

`Stage6ClosedLoopRunner.run_task(...)` calls the Controller only after all of the following are true:

- planning produced a concrete `Plan`
- plan task matches the requested task
- unresolved DC3PA outcome did not trigger `block`
- no pre-execution planner failure prevented a plan

The emitted event immediately before Controller execution is `plan_ready_for_controller`.

## When Successful Memory Is Written

Successful memory writes occur only inside the `goal_success` branch in `Stage6ClosedLoopRunner.run_task(...)`.

Ordering is:

1. Controller returns `ExecutionResult(success=True, ...)`
2. Goal checker runs if `require_goal_check=True`
3. only if `goal_success=True`, the runner calls `_record_success_memories(...)`

Therefore memory is written after verified goal success, not merely after Controller success.

## Current Interface Risks For The Controlled Test

1. `EnvironmentReliabilityStrategy` returns unavailable when there is no current image or no compatible exemplar signal.
   The controlled test must deliberately keep `pE` unavailable and assert that this is expected, not an error.
2. `EvaluationReport.from_dict(..., expected_plan=...)` rejects stale `plan_id`, stale `plan_version`, and unknown `step_id`.
   The deterministic evaluation provider must construct edits using the actual current mine step ID from the incoming request.
3. `Stage6ClosedLoopRunner` does not expose all planning diagnostics in `TaskRunResult` directly.
   The controlled test will need to capture diagnostics through the real trace file and/or a wrapper around the real reasoning/evaluation/controller objects without modifying production code.

## Pass 1 Decision

The repository interfaces are sufficiently stable for a deterministic Stage 6 controlled cobblestone test without modifying production logic.
